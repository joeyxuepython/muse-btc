# 信号的决策解释与规则衔接

只显示涨幅、放量和规则分数，无法判断候选是否经过风险检查。新版本将实时/回放入口实际执行的检查保存到每个信号的 `decision` 字段，预警、不可变通知和发送组沿用这份记录。网页可查看全部评估及来源，中文消息说明本次变化、触发依据、通过的检查、限制、缺项及研究背景。

## 各类信息如何参与

| 信息 | 实际用途 |
| --- | --- |
| 基础规则输入与 A–F 子模式 | 生成风险、观察或机会候选。保存实际匹配结果和当时输入；子模式共享数据，不能当作六套独立策略投票 |
| Funding、OI、价差、时间对齐和 BTC 风险状态 | 使用已有规则的门控条件，保存实际布尔检查；不同规则的检查范围不同，未执行的检查不会补成通过 |
| 负面催化、七日内解锁 ≥5%、FDV/流通市值 >10 | 原有融合规则的资产风险否决同步用于现货动量；两者均降为 WATCH，不发布 STRONG。正面催化仍只给融合规则增加证据组 |
| 宏观流动性代理与 ETF | 保留两者同向收缩使 BTC 进入 CAUTION 的已有门控；未知只说明无法完整核实，不声称宏观环境安全 |
| MVRV、历史 SOPR/短持成本、期权、研究、稳定币及基本面 | 说明状态、输入、局限与来源；未纳入短期触发的部分明确标为背景，不补造新的策略票数。BTC 研究观察仍为 WATCH |
| 机会排行与实验模型 | 排行只排序；实验模型未进入生产信号，不生成或放行候选 |
| 社交/KOL、钱包、DEX/Intent/Solver、完整清算、宏观事件反应 | 未参与本候选决策。本轮未检查这些独立模块是否已采集，不能描述成全部已使用或全部缺失 |

新增资产否决也会结束已有候选，关联原信号并保存本次原因及来源；仅对原通知有 SENT 回执、仍在观察期限内的候选发送撤销。普通 WATCH 失效保持归档，旧候选不会因背景改善而自动恢复。读取待发送机会时再次检查最新已归档资产风险，出现阻断返回 `SKIP_CONTEXT_BLOCKED`，避免等待下一轮主采集期间误发；真正的市场风险提醒不受此机会门控影响。

缺失资产背景沿用原规则，不自动否决机会，但标为 UNKNOWN；“未发现已知阻断”不能视作全面核实。催化未核实或事件已超过七天不参与支持/否决。tokenomics 尚无自动过期策略，消息注明使用已录入观测，详情保留记录时点和不完整字段；基本面收入、TVL、用户数没有新增短线权重。

BTC 上下文版本为 `btc-context-v3`：修正流动性变化的美元换算，WALCL/TGA 的百万美元与 RRP 的十亿美元统一转成美元后展示；符号和已有 CAUTION 条件不变。旧归档不改写，旧版本金额不能与新版本直接按同一单位比较。

## 保存的内容

`decision.version=decision-explanation-v1`，包含：

- `as_of`、`snapshot_id`、观察/可用时点、组件时点、原始数据 ID。
- `triggered`、`evaluations`：本规则、匹配子模式及同轮其他实际评估；结果包含未启用、不适用、缺失、未触发和触发状态。决策阶段不声称已发布或已发送。
- `gates`、`data_gaps`：实际检查结果，区分本规则、其他规则和背景的缺项；已保存但过期的输入与原本缺失的输入分别标记。旧式快照没有组件时点时注明历史兼容限制。
- `btc_regime`、`asset_context`、`background`：BTC 门控依据、资产风险检查及八维 BTC 研究背景。来源 ID、来源链接、观察/可用时点随评估保留。
- `coverage`：本规则和匹配子模式的非缺失输入字段数；不是来源覆盖、独立策略数量或胜率。
- `publication`：预警发布级别、pre-pump 确认结果/涨幅/时限及排序用途。发布检查由 `publish_alert` 添加；不是邮件回执。
- `not_integrated`、`limitations`、`conditions`：未进入决策的模块、局限及原有失效条件。

通知中的决策记录保持不可变；最新告警可以刷新自己的决策，通知读取中的 `current_asset_context` 是发送时复核结果，不覆盖旧通知的 `decision`。来源在当时不可用的记录不能参与；不同时间的排行缓存不复用为当前资产证据。生命周期通知使用独立 `LIFECYCLE` 记录，引用原决策时点，不复制旧看涨理由作为当前触发。

旧记录没有决策链时明确显示未知，不用最新诊断补写历史。价格、排行、Funding 等数字小幅变化以及背景研究刷新不新增通知；门控状态、证据组合、级别等明确变化仍按原增量队列处理。同币消息去重共同背景并保留每条规则和全部通知 ID。

## Muse 云端接入与验收

合并并更新云端代码后，保持现有邮件连接、API 口令、持久化游标及发送回执。无需新增定时任务或立即运行研究采集。

1. 确认 `/health` 与 `/api/alerts/notifications` 返回 `decision_explanation_version=decision-explanation-v1`；原 `delivery_policy_version=meaningful-change-v2` 保留。
2. 按[已有批次流程](strategy-observability.md)排空通知后调用 `fetch_notification_batch`。每个组新增 `decision_explanations`；正文直接采用组的 `message_zh`，不要再只摘取涨幅、放量和分数。只有 READY 的成员进入发送组。
3. 候选正文应有本次变化、真实触发条件、通过的门控、数据缺项、BTC 背景、仅作背景的研究及未参与模块；网页的“本轮决策链”可核对细项及原始来源。
4. 发送前仍复核报价/时限/级别与上下文阻断；按全部成员 ID 写回执，保持失败重试和安全水位。已发候选因资产风险撤销时，核对父通知 SENT 回执与候选观察期限。

代码版本、离线检查和网页合成数据预览不证明云端持续采集、真实邮件送达或交易收益。实际数据覆盖及 Muse 是否采用新正文需在云端验收。
