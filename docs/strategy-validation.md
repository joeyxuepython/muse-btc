# Muse 指引：按策略声明评估期限

更新日期：2026-10-06。对应 PR 合并后部署；本地检查不能代替云端验收。

## 本次解决的问题

过去验证器给所有规则安排 5 分钟到 30 天的九个期限。期限没有按策略声明，卖压告警也沿用价格收益表。现在新信号生成时保存自己的指标、主评估期、辅助观察期和设计理由；队列、手动验证、重放和网页都只使用该信号归档的声明。

**五分钟负收益不会自动否定入场候选。** 核对原实现后，验证器本来就不按收益修改生命周期。本次把这个区别明确写入 API、通知正文和网页，避免把早期表现记录误读为退出指令。真实价格跌破失效参考位、BTC 风险变化、连续买入支撑消失等仍可以提前撤销；不能因为评估期尚未结束就屏蔽真实风险。

## 规则的声明

| 规则 | 主评估 | 辅助观察 | 评估对象及依据 |
| --- | --- | --- | --- |
| `pre-pump-fusion` | 15 分钟 | 5 分钟 | 5/15 分钟启动结构；短时价格表现 |
| `spot-led-momentum` | 1 小时 | 5、15 分钟 | 成交与 EMA 趋势；价格表现及短期路径 |
| `squeeze-candidate` | 15 分钟 | 5 分钟 | 5 分钟价格/OI 的短时挤压假设 |
| `spot-sell-pressure` | 15 分钟 | 无 | 15 分钟卖压后，终点/采样窗口是否下跌 |
| `leverage-overheat` | 1 小时 | 15 分钟 | Funding/OI 过热后，方向与风险路径 |
| `btc-macro-stress` | 1 天 | 无 | 日频宏观/ETF 风险背景；保持原观察尺度 |
| `btc-mvrv-elevated` | 1 天 | 无 | 日频链上估值背景；保持原观察尺度 |
| `btc-holder-loss` | 1 天 | 无 | 日频持有人成本/亏损背景；保持原观察尺度 |
| `btc-options-volatility` | 4 小时 | 无 | 期权波动背景；采样范围、终点绝对变化 |

这些期限是依据输入尺度明确提出的**待检验设计**，不是通过历史收益挑出的最优持有期，也没有证明比其他期限有效。主指标不能被盈利的辅助期限替换；主期限没有价格覆盖就报告缺失。修改声明只影响之后生成的信号，已有信号和结果不回写。

`LONG_RETURN`：入场候选可计算固定费用/滑点后的纸面价格变化、双倍成本对照；同指标的 WATCH 只观察价格，不计为入场收益。

`RISK_DIRECTION`：报告终点下跌占比、Wilson 描述区间、窗口曾下跌占比、最大采样跌幅和反向上涨。没有持仓收益、做空收益或往返费用。下跌定义为相对告警参考价小于零，轻微噪声也可能计入；窗口曾下跌是辅助路径指标，不是告警的交易成功率。没有与同时段随机/无告警样本比较，不能声称有增量预测能力。

`VOLATILITY`：只报告采样范围及终点绝对变化，不推断涨跌或持仓收益。这不是实现波动率估计，也没有证明 IV 对未来波动的预测能力。

所有采样路径仍须满足覆盖检查，可能遗漏采样间的盘中极值。当前仍是 `OBSERVATION_ONLY`；没有模拟实际成交、止损、退出或用户持仓，不会自动晋级策略。

## 四种时间不要混用

1. 主评估/辅助观察：`signal.evaluation` 中预先保存的价格检查时点，只生成 Outcome，不改变信号状态。
2. 候选有效期：`signal.expires_at`；基础市场候选仍沿用原四小时上限。真实条件可提前使其失效。
3. 首次发现后的确认/投递时限：pre-pump 原五分钟限制保留，用于防止迟到确认和追涨发送，不是买入后只能持有五分钟。
4. 已发通知的撤销更新窗口：沿用现有回执及期限限制，避免过期候选刷屏；不是止损价格或自动卖出条件。

旧字段 `signal.horizon_seconds` 保留用于既有通知分组和撤销窗口兼容。**新策略的主评估期读 `evaluation.primary_horizon_seconds`，允许期限读 `evaluation.horizons_seconds`**，不要从旧字段推导新验证期限。同币的 pre-pump 与现货动量继续合并提醒，各自的计划随组内成员保留。

## API 与历史兼容

- `/api/signals/{id}`：`signal.evaluation`、`evaluation_policy_id`、`evaluation_lifecycle_note`，以及归档 `outcomes`。
- 新告警/冻结通知：`evaluation` 和 `evaluation_policy_id`；合并投递的 `evaluation_plans` 按 `notification_id` / `rule_id` 保存每个成员的计划。Muse 沿用 `message_zh`，不要自行把五分钟表现转换成撤销或卖出。
- `/api/validation` / `muse validate`：版本 `validation-v3`。`rules` 按规则版本、类型、模块及计划指纹分组；每个声明期限固定输出一行。`horizon_role` 为 `PRIMARY` 或 `AUXILIARY`，分别列待到期、缺失终点、断档和去重样本数。
- `legacy_rules`：旧信号没有完整声明，保留实际已有的各期限结果和旧观察窗，标为 `LEGACY_OBSERVATION`；旧负收益仍能查到，不与新声明混算。不能把新报告暂时无结果解释为旧负收益消失或策略改善。
- `out_of_plan_outcome_count`：新信号已有结果中，期限、计划指纹或指标不匹配声明的数量。这些结果保留在原始详情，不进入新计划统计。

新信号必须声明计划，遗漏时明确报错。旧信号只继续其归档 `horizon_seconds` 所指定的单个观察窗，不套用今天的策略期限。旧队列中其他尚未完成或缺失的任务标为 `RETIRED_POLICY`，不再扫描价格；已完成结果不删除、不改写。`--retry-missing` 不会重新激活已退役期限。

后台每批最多迁移 64 条旧信号，并使用独立的 `validation_policy_seed_cursor`；之前的队列回填游标不能跳过此次迁移。尚未迁移的到期任务也会在读取历史价格前检查期限。手动 `muse validate` 可完成迁移，但仍会遍历归档生成报告，长历史上应避免与频繁 API 轮询重复运行。

## Muse 更新与验收

1. PR 合并后，先按[云端运行指引](cloud-run.md)备份数据库、检查本地改动，再更新 main、重新安装并按原方式重启。保留 `.env`、数据库、邮件连接、通知回执和已有游标；研究定时监控保持暂停。
2. 沿用[独立验证 worker](collector-latency.md)，通过 `muse runtime` 查看心跳和队列。等待逐批迁移；`RETIRED_POLICY` 增加是取消旧九期限套餐，不是采集失败。不要删除数据库重建样本。
3. 保存 `muse validate` 或认证 `GET /api/validation` 的完整 JSON，确认 `version=validation-v3`。新 pre-pump 只有 5/15 分钟行，15 分钟为 `PRIMARY`；新现货动量只有 5/15/60 分钟行，60 分钟为 `PRIMARY`。
4. 检查新卖压/杠杆过热的 `RISK_DIRECTION` 结果，`paper_net_return_pct`、`round_trip_cost_bps` 应为 null；报表展示下跌/反向上涨，不把价格变化写成跟单收益。
5. 核对五分钟 Outcome、`signal.events` 和实际撤销原因。负收益本身不能产生 INVALIDATED；若真实价格阈值、风险条件已触发，保留原始事件与行情证据，不强行维持候选。
6. 保留旧 `legacy_rules`、新主/辅助结果、缺失/断档、计划指纹和实际通知样例供比较。本地回归只证明口径及兼容行为，云端性能、邮件送达、未使用过的样本外表现与优于随机仍需真实证据。

本地核验见[验证记录](verification/strategy-validation.md)。
